# ADR-001 — Окончателно архитектурно решение

> Статус: **ПРИЕТО** · 26.08.2026
> Заменя сравнителния анализ в [01-strategy-and-architecture.md](01-strategy-and-architecture.md), който остава като обосновка.

## 1. Контекст и граници

- Старият PHP сайт **не се кърпи и не се доразвива**. Той е източник на информация, не основа.
- Използва се за: анализ на данните, миграция, брандова цветова идентичност, URL структура,
  списък със стари грешки, които да не повтаряме.
- Целта е **нов backend и нов frontend**.
- **10.09.2026 = soft launch с ограничен обхват.** Не е финален launch.
- **Пълен launch: октомври 2026** — целият каталог, всички 301 редиректи, стабилна операция.

## 2. Решение

| Слой | Технология | Роля |
|---|---|---|
| Commerce core | **Medusa v2** | продукти, варианти, наличности, цени, промоции, поръчки, плащания, доставки, връщания, клиенти |
| База | **PostgreSQL 16** | две отделни бази на един инстанс (виж 2.1) |
| Кеш / опашки | **Redis 7.2 (Valkey)** | Medusa workflows, event bus, сесии, rate limiting |

| Хостинг | **Vercel** (storefront) + **Hetzner EU-Central** (Medusa, Redis, Meilisearch) | |

| Език | **TypeScript strict** навсякъде | |

### 2.1. Две отделни бази, един Postgres инстанс

`fabrizia_commerce` (Medusa) и `fabrizia_cms` (Payload).

**Защо не една база с два schema-та:** и Medusa, и Payload управляват собствени миграции. Споделен
schema означава, че миграция на едното може да заключи или да счупи другото, и че при restore не можеш
да върнеш само едното. Отделните бази дават независим backup/restore и нулев риск от колизия при
миграции. Цената е един JOIN по-малко — но ние и без това не join-ваме съдържание с пари.

**Връзката между двете е по ID, не по foreign key.** CMS блокът `ProductRail` пази списък от
Medusa product handle-ове; storefront-ът ги резолвва при рендер. Ако продукт бъде изтрит, блокът го
пропуска и логва warning — не хвърля 500.

### 2.2. Структура на репото (монорепо, pnpm workspaces)

```
/apps/backend        Medusa v2
/apps/storefront     Next.js 15 + Payload 3 (в едно приложение)
/packages/shared     споделени типове, константи, SKU логика, транслитерация
/packages/config     eslint, tsconfig, prettier базови конфигурации
/infra               docker-compose.dev.yml, деплой скриптове, runbook
/docs                този план и последващата документация
```

Payload живее **вътре** в storefront приложението (`/apps/storefront/src/payload`), защото Payload 3 е
Next.js-native: един deploy, един процес, споделени типове, `/admin` route идва наготово.

## 3. Версии за pin-ване

**Правило: без `^` и без `~` в `package.json`.** Точни версии, `pnpm-lock.yaml` в git,
Docker образи по digest, не по таг.

| Компонент | Pin | Бележка |
|---|---|---|
| Node.js | **22.x LTS**, фиксиран в `.nvmrc` и `engines` | не мигрираме към 24 преди пълния launch |
| pnpm | точна версия през `packageManager` + corepack | |
| TypeScript | 5.x, точна | `strict: true`, `noUncheckedIndexedAccess: true` |
| Medusa | **точната стабилна 2.x към деня на init** | всички `@medusajs/*` пакети на една и съща версия |
| Next.js | **15.x, точна** | без canary |
| React / React DOM | **19.x, точна** | |
| Payload | **3.x, точна** + `@payloadcms/db-postgres` от същата версия | |
| Tailwind CSS | **4.x, точна** | |
| PostgreSQL | **16.x** | managed; 17 чак след пълния launch |
| Redis / Valkey | **7.2.x** | |
| Meilisearch | **1.x**, точен minor | индексът се реиндексира при смяна на minor |
| Stripe SDK | точна версия + **pinned API version** (`apiVersion: "YYYY-MM-DD"`) | API версията се фиксира в кода, не се наследява от акаунта |

**Как се фиксират точните числа:** на ден 1, при `pnpm create`, записваме реалните инсталирани версии
в `docs/VERSIONS.md` и в лока. Никой не ъпгрейдва след това без отделно решение.

### Политика за ъпдейти

- **От 28.08 до 10.09 — пълно замразяване.** Само security patch с доказан CVE, който ни засяга.
- Renovate/Dependabot: включен, но само отваря PR-и; нищо не се мърджва автоматично.
- След soft launch: един ъпдейт прозорец седмично, вторник сутрин, никога петък.
- Медуса major/minor ъпгрейд — само между кампании, с пълен регресионен тест.

## 4. Окончателни решения (не се преразглеждат)

1. Medusa v2 е commerce core. Vendure отпада.
2. Next.js 15 App Router е storefront. Няма SPA, няма отделен client-only рендер.
3. Payload 3 е CMS, вътре в storefront приложението.
4. Две отделни Postgres бази.
5. **Едно продуктово ID = един модел в един цвят.** Размерите са варианти. Цветовете се групират
   през StyleGroup и всеки има собствен URL.
6. **SKU схема:** `FB-{модел}-{цвят}-{размер}`, напр. `FB-2601-BLK-S`. Уникален, immutable след
   първата поръчка.
7. **EUR е базовата валута.** BGN само като справочно изписване, докато е задължително.
8. **Guest checkout е задължителен.** Регистрацията никога не е условие за поръчка.
9. **Два админ панела на един домейн** за soft launch. Обединяване — фаза 2.
10. Наличността никога не се рендира в статичния HTML.
11. Всяка външна интеграция е зад интерфейс: `ShippingProvider`, `PaymentProvider`,
    `AccountingExporter`, `FeedGenerator`. Смяна на доставчик не докосва UI.
12. Медия само в R2. Никога в git, никога на диска на приложението.
13. Съдържание и визия се менят само от CMS. **Ако нещо изисква deploy, за да смени снимка — това е бъг.**
14. TypeScript strict, без `any`. `unknown` + валидация на границите.
