Кодът не е тясното място. Тясното място са **външните срокове**, които не зависят от разработчика:

**0.2. Валута.** България е в еврозоната от 01.01.2026. Магазинът се строи с **EUR като базова валута**
от първия ден, с двойно изписване EUR/BGN докато то е задължително. Това не е „после ще оправим“ —

## 1. Каква система реално ти трябва

Не ти трябва „нов сайт“. Трябва ти **четири отделни системи с ясни граници**, за да може всяка да се
сменя без да чупи останалите. Точно това е грешката на стария PHP сайт — всичко е едно.

```
┌────────────────────────────────────────────────────────────────────┐
│  1. COMMERCE CORE  (истината за пари и наличности)                 │
│     продукти · варианти · наличности · цени · промоции · поръчки   │
│     плащания · доставки · връщания · клиенти                        │
│     → Medusa v2 + PostgreSQL                                        │
└────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────┐
│  2. CONTENT / BRAND LAYER  (истината за визията)                   │
│     hero банери · колекции · lookbook · landing pages · менюта     │
│     footer · SEO текстове · сезонни теми и цветове                  │
│     → Payload CMS 3 (в същото Next.js приложение, същия Postgres)   │
└────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────┐
│  3. STOREFRONT  (това, което клиентът вижда)                       │
│     Next.js 15 (App Router) · React Server Components · ISR         │
│     → Vercel или Cloudflare, зад CDN                                │
└────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────┐
│  4. INTEGRATION LAYER  (мостовете навън)                            │
│     Еконт/Спиди · платежен доставчик · счетоводство (Ажур L/ОРАК)   │
│     Google Merchant · Meta CAPI · имейл · Meilisearch               │
│     → изнесени като отделни модули/workflows, никога в UI кода      │
└────────────────────────────────────────────────────────────────────┘
```

Правилото, което спасява проекта: **Commerce core не знае нищо за визия. Content layer не знае нищо за
пари.** Смяната на сезонната визия не докосва база с поръчки. Смяната на счетоводен софтуер не докосва
storefront-а.

### 2.2. Какво реално тежи във всяка опция

**Medusa v2** — печели, защото 90% от нещата, които иначе ще пишеш 3 месеца, вече ги има и са
правени правилно: резервации на наличност при поръчка (не „минус от количеството“), price lists,
promotion rules engine, stock locations, fulfillment providers като плъгини, връщания и размени,
tax regions, sales channels. Workflow engine-ът (`createWorkflow` + compensation steps) е точно
инструментът за интеграция със счетоводство и куриери — стъпка, която се повтаря при грешка и се
компенсира при отказ, без ръчно чистене. Минусите са реални: админът не е CMS, българските неща
(Еконт/Спиди, ДДС фактура, наложен платеж) се пишат от нас, и трябва да пиннеш версия и да не
ъпгрейдваш по време на кампания.

**Saleor** — технически най-зрелият, но плащаш с втори стек (Python), по-тежък self-hosting и
по-трудно писане на кастъм логика (всичко минава през „apps“). За един български бранд с един склад
това е инженерство за проблем, който нямаш.

**Laravel + Lunar + Filament** — единствената причина да го избереш е **екипът**. Ако хората, които
ще поддържат това след старта, са PHP разработчици, Laravel е по-добър избор от „правилния“ Medusa,
защото поддържаният код бие елегантния код. Но бъди наясно: ще пишеш сам резервации на наличност,
промоционален engine и връщания — това са точно местата, където се раждат багове с реални пари.

**Изцяло custom NestJS** — не. Това е 6–9 месеца, за да стигнеш до там, откъдето Medusa започва.

**Vendure** — честната алтернатива №2. Ако при прототипа Medusa v2 те подразни с нестабилно API,
Vendure е по-консервативен и по-стриктен. Решението се взима на ден 3 (виж spike-а в документ 02).

### 2.3. ПРЕПОРЪКА

```
Commerce core : Medusa v2            (Node 22, TypeScript)
База          : PostgreSQL 16        (managed — Neon или Hetzner + PITR бекъпи)
Кеш/опашки    : Redis (Valkey)
Търсене       : Meilisearch          (self-hosted; Algolia само ако бюджетът позволи)
Content/CMS   : Payload CMS 3        (в същото Next.js repo, същия Postgres)
Storefront    : Next.js 15 App Router + TypeScript + Tailwind
Медия         : Cloudflare R2 + image CDN (AVIF/WebP, responsive srcset)
Инфраструктура: Vercel (storefront) + Hetzner EU-Central (Medusa+Redis+Meili), Cloudflare отпред
Наблюдение    : Sentry + Better Stack (uptime) + Vercel Analytics
```

**С една уговорка:** ако човекът, който ще поддържа сайта след 6 месеца, е PHP разработчик и няма да
наемате Node човек — сменяме на Laravel + Lunar + Filament и приемаме +4 седмици. Кажи ми това преди
да напишем първия ред код.

## 3. Frontend

**Next.js 15, App Router, React Server Components, TypeScript, Tailwind CSS.**

Защо не Astro/Remix/Nuxt: Next има най-зрелите e-commerce патърни, ISR на ниво страница/таг
(`revalidateTag('product:123')` при промяна на наличност), най-голям talent pool и най-добра
интеграция с Vercel Image/Edge. Payload 3 се хоства вътре в същото Next приложение — един repo,
един deploy, споделени типове.

### Рендер стратегия (това определя скоростта при реклами)

| Тип страница | Стратегия | Инвалидация |
|---|---|---|
| Начална, landing, lookbook | Static + ISR 5 мин | webhook от CMS при publish |
| Категория / PLP | Static + ISR 5 мин, филтрите → URL search params (споделяем линк, SEO-friendly) | таг `category:{slug}` |
| Продукт / PDP | Static + ISR 5 мин; **наличността се дозарежда client-side** | таг `product:{id}` при промяна на stock |
| Кошница, checkout, профил | 100% динамично, без кеш | — |
| Търсене | client-side към Meilisearch, `noindex` | — |

Наличността никога не се вгражда в статичния HTML — иначе показваш „в наличност“ на разпродаден
размер. Статичен скелет + едно бързо клиентско повикване за stock.

### Performance бюджет (не е пожелание, а критерий за приемане)

- LCP на мобилен 4G: **< 2.0s** (цел 1.6s)
- INP: **< 200ms** · CLS: **< 0.1**
- JS на PDP: **< 180 KB** gzip
- Първо изображение: AVIF, priority, точен `sizes`, LQIP blur placeholder
- Шрифт: 1 семейство, 2 тежести, `next/font` self-hosted, `font-display: swap`, без FOUT скок
- Бюджетът се проверява автоматично на всеки PR (Lighthouse CI). PR, който го чупи, не се мърджва.

### Визуален език — как да изглежда като голям бранд, а не като малък магазин

Разликата между Mango/COS и „обикновен онлайн магазин“ е в 6 неща, не в цветовете:

1. **Снимката е интерфейсът.** Full-bleed, без рамки, без сенки, без градиенти. Продуктовите снимки
   са в едно съотношение (**3:4**), един фон, един кроп. Едно неконсистентно изображение убива
   премиум усещането повече от лош шрифт.
2. **Много празно пространство.** Базова скала 8px, но външните отстъпи са 64/96/128px на десктоп.
3. **Типография с контраст:** едно неутрално grotesque семейство (Söhne / Inter Tight / Suisse),
   заглавия с `letter-spacing: -0.02em`, навигация в UPPERCASE с `letter-spacing: 0.08em`, size 11–12px.
4. **Почти без цвят в UI-а.** Черно, бяло, 3 сиви. Цветът идва само от снимките. Акцентният цвят на
   Fabrizia се пази за 3 неща: sale етикет, CTA hover, focus ring.
5. **Никакви декорации.** Без border-radius над 2px, без box-shadow, без иконки-емоджита, без
   „🔥 ХИТ“ бадж. Sale етикетът е малък текст, не червен балон.
6. **Движение:** само `opacity` и `transform`, 200–300ms, `cubic-bezier(0.4, 0, 0.2, 1)`. Нищо, което
   подскача.

Реалната цветова гама на Fabrizia влиза в системата като design tokens (виж т. 5) — **не бягаме от
бранда**, но UI хромът става неутрален и цветът се използва точково. Точните HEX стойности ще извадя
от стария сайт, когато го получа.

### Задължителни компоненти на storefront-а за MVP

Header със sticky mini-cart · мега-меню по категории с промо изображение · PLP с филтри
(размер, цвят, цена, наличност) и сортиране · PDP с галерия (zoom, 5+ снимки, вертикален thumbnail
рейл на десктоп, swipe на мобилно) · size selector с „няма наличност“ състояние · size guide modal ·
„моделът носи размер S, височина 176 см“ · sticky add-to-cart на мобилно · cart drawer · 3-стъпков
checkout · order confirmation · статични легални страници · 404 с продуктови препоръки.

## 4. Админ панел

### Честният отговор: два панела, които изглеждат като един

Няма как един панел да е едновременно добър commerce backend и добър page builder, без да напишеш
6 месеца код. Затова:

| | **admin.fabriziafashion.bg/shop** (Medusa Admin) | **admin.fabriziafashion.bg/content** (Payload CMS) |
|---|---|---|
| Кой го ползва | оператор поръчки, склад, мениджър | маркетинг, съдържание |
| Какво управлява | продукти, варианти, наличности, цени, промоции, поръчки, статуси, клиенти, доставки, промо кодове, отчети | начална страница, hero банери, колекции, lookbook, landing pages, менюта, footer, легални текстове, SEO текстове |
| Влизане | един и същ домейн, отделен login | същият домейн |

Един bookmark, едно и също лого, еднакви цветове, линк за превключване горе вдясно. За оператора,
който 90% от времето е в „Поръчки“, това е един панел. **Обединяване в един shell е задача за фаза 2**,
не за MVP — визуалното обединение струва 2 дни, истинското 4 седмици.

### Какво трябва да може админът (пълен списък, съпоставен с изискването ти)

**Продукти** — създаване/редакция, богат текст описание, състав и грижа, размерна таблица, категория,
колекция, тагове, статус (чернова/публикуван/архивиран), масов импорт от CSV, дублиране на продукт.
**Варианти** — генератор размер × цвят; SKU по схема; отделна цена и наличност на вариант.
**Наличности** — по локация (склад / магазин), ръчна корекция с причина и одит log, праг за „последни
бройки“, автоматично скриване на изчерпан вариант.
**Цени и намаления** — редовна цена, промо цена, период на промоцията (стартира и спира сама),
price list за конкретна колекция, показване на „беше“ цена.
**Категории и подкатегории** — дърво с drag & drop, собствен hero банер и SEO блок на всяка категория,
ръчно подреждане на продуктите вътре (merchandising) + правила („изчерпаните най-долу“).
**Снимки и галерии** — drag & drop качване, пренареждане, alt текст (задължително поле), автоматично
генериране на AVIF/WebP в 5 размера, задължителен кроп 3:4 с warning при друго съотношение.
**Начална страница / hero / сезонни секции** — виж т. 5.
**Колекции** — SS26, „Нови постъпления“, capsule колекции; всяка с корица, hero, описание и
собствен URL.
**Поръчки** — списък с филтри (статус, дата, куриер, стойност, плащане), детайл, редакция преди
изпращане, частично изпращане, генериране на товарителница с 1 бутон, печат на пакинг лист,
отбелязване на плащане, сторниране, връщане, вътрешни бележки, история на действията (кой какво кога).
**Статуси на поръчки** — виж т. 6.
**Клиенти** — профил, история на поръчки, LTV, GDPR експорт и изтриване с 1 бутон.
**Доставки** — куриери, цени, безплатна доставка над сума, зони, тегло, работа с офиси/автомати.
**Промо кодове** — код, тип, стойност, минимална поръчка, лимит общо/на клиент, период, обхват
(категория/колекция/продукт), еднократни кодове за инфлуенсъри.
**Отчети (базови за MVP)** — оборот по ден/седмица/месец, брой поръчки, средна стойност, топ 50
продукта, разбивка по куриер и по метод на плащане, брой непотърсени пратки, наличност под праг.
**SEO** — на всеки продукт/категория/колекция/страница: meta title, meta description, slug, canonical,
OG изображение, `noindex` чекбокс; + отделен екран „301 пренасочвания“ с масов CSV импорт.
**Менюта и footer** — drag & drop, линк към категория/колекция/страница/външен URL, колони на footer,
социални мрежи, платежни икони.

### Роли

`owner` (всичко) · `manager` (без изтриване, без роли) · `content` (само CMS) ·
`fulfillment` (само поръчки и наличности, не вижда обороти) · `finance` (само поръчки, плащания, отчети).

## 5. Сезонна смяна на визията без нито един ред код

Това е изискване №1 от гледна точка на дългосрочна поддръжка, затова го проектираме нарочно, не
случайно. Три слоя:

### Слой 1 — Design tokens (сменяш „температурата“ на целия сайт)

В Payload има колекция **„Тема“** с полета, които се компилират в CSS custom properties и се
инжектират в `<html>`:

```
--brand-ink        основен текст / черно на бранда
--brand-paper      фон на страницата (напр. топло бяло през есента, студено през лятото)
--brand-accent     акцент (CTA hover, focus, sale)
--brand-muted      второстепенен текст
--brand-sale       цвят на намалението
--radius           0px / 2px
--font-display     заглавен шрифт (от одобрен списък)
--type-scale       compact / regular / editorial
```

Марк маркетингът избира тема „SS26“ или „AW26“ от dropdown и целият сайт се променя — без deploy.
Темата има поле **`activeFrom` / `activeTo`**, така че смяната се пуска в 00:01 на 1 септември сама.

### Слой 2 — Block-based page builder (сглобяваш страници като лего)

Началната страница и всяка landing page е **списък от блокове**, които маркетингът подрежда с
drag & drop. Готовите блокове за MVP:

| Блок | Полета | Ползва се за |
|---|---|---|
| `HeroFull` | desktop image, mobile image, video (по избор), заглавие, подзаглавие, до 2 CTA, позиция на текста (9 точки), цвят на текста (светъл/тъмен), overlay 0–60% | главен сезонен банер |

| `ProductRail` | заглавие + източник (колекция / категория / ръчен списък / „нови“ / „намалени“) + брой | „Нови постъпления“ |
| `EditorialTwoUp` | 2 изображения + текст отстрани | lookbook секция |
| `LookbookGrid` | 3–12 изображения с hotspot-ове към продукти | „Shop the look“ |
| `CategoryTiles` | 2–6 плочки с изображение и надпис | навигация от началната |
| `TextBanner` | текст + фон + линк | „Безплатна доставка над 100 €“ |

Всеки блок има **`visibleFrom` / `visibleTo`** и **`visibleOn: [desktop, mobile]`**. Кампанията се
подготвя седмица по-рано, планира се и се пуска сама.

### Слой 3 — Preview и безопасност

- **Draft + Live Preview**: маркетингът вижда точния резултат преди publish, на отделен URL с токен.
- **Версии и rollback**: всеки publish е версия; връщане една стъпка назад с 1 бутон.
- **Scheduled publish**: „публикувай в 00:01 на 01.09“.
- **Инвалидация**: publish → webhook → `revalidateTag` → страницата е нова до 5 секунди, без deploy.
- **Guardrails**: изображенията се проверяват за минимални размери и съотношение; ако липсва alt текст,
  publish е блокиран. Така маркетингът не може случайно да счупи Core Web Vitals.

**Тест за приемане на това изискване:** човек без техническо образование, за 40 минути, само от админа,
трябва да смени hero банера, да пусне нова колекция с 12 продукта и да планира промо страница за
следващия петък. Ако не може — не е готово.

## 6. Поръчки, наличности, склад и доставки

### 6.1. Модел на каталога (важно решение за fashion)

**Едно продуктово ID = един модел в един цвят.** Размерите са варианти. Цветовете се групират през
`styleGroup` (общ код на модела) и се показват на PDP като „цветови суичър“, който води към отделен URL.

Точно така работят Zara/Mango — всеки цвят има собствена галерия, собствен URL, собствено SEO и
собствен фийд ред към Google. Алтернативата (цвят като вариант) чупи галерията и фийда.

```
StyleGroup: FB-2601 "Рокля Elena"
 ├─ Product FB-2601-BLK "Рокля Elena — черна"   → /produkt/rokla-elena-cherna
 │   └─ Variants: XS S M L XL  (SKU: FB-2601-BLK-S)
 └─ Product FB-2601-CRM "Рокля Elena — кремава" → /produkt/rokla-elena-kremava
     └─ Variants: XS S M L XL
```

SKU схема: `FB-{модел}-{цвят}-{размер}` — чете се от човек, работи в склада, работи в счетоводството.

### 6.2. Наличности — правилото, което пази от overselling

Никога „количество минус едно“. Три числа на вариант:

```
on_hand        физически в склада
reserved       заделено за платени/приети, но неизпратени поръчки
available      = on_hand − reserved   ← това вижда клиентът
```

- Резервацията се прави при **успешно създаване на поръчка**, не при добавяне в кошницата.
- `on_hand` намалява при **потвърдено изпращане**, не по-рано.
- Отказана/непотърсена пратка → връщане в наличност с отделна причина (за отчет).
- Всяка ръчна корекция иска причина и се записва в одит log.
- Праг `low_stock_threshold` → „последни бройки“ на PDP + известие в админа.
- Съществува offline канал (физически магазин?) → **фазa 2** е двупосочна синхронизация. За MVP:
  единен склад + ежедневен CSV сравнителен отчет.

### 6.3. Жизнен цикъл на поръчката (BG-специфичен)

```
draft → pending_payment ──(карта ok / наложен платеж)──→ confirmed
                              └──(карта fail)──→ failed
confirmed → picking → packed → label_created → shipped → in_transit
                                                          ├─ delivered → completed
                                                          ├─ unclaimed  (непотърсена — статус,
                                                          │              който ТРЯБВА да съществува)
                                                          └─ refused    (отказана при доставка)
delivered → return_requested → returned → refunded
всеки статус → cancelled (с причина)
```

`unclaimed` и `refused` не са екзотика — при наложен платеж в BG fashion те са 8–20% от поръчките и са
най-големият скрит разход. Затова са отделни статуси от ден 1, влизат в отчета и подготвят
COD-risk скоринга от фаза 2.

### 6.4. Доставки — конкретика за България

**Еконт** и **Спиди** — и двата, от MVP. И двата имат REST API.

Задължително в checkout:
- избор „до офис / до автомат / до адрес“;
- **търсачка на офиси и автомати с карта** (не dropdown с 3000 реда);
- изчисляване на цената на живо според тегло/обем и метод;
- за наложен платеж — сумата за събиране се подава към куриера автоматично;
- опция **„преглед и тест“** (Еконт) / „преглед“ (Спиди) — за дрехи това пряко вдига конверсията и
  трябва да е ясно обозначено на PDP, не скрито в checkout;
- генериране на товарителница от админа с 1 бутон + печат;
- webhook за проследяване → автоматична смяна на статус и имейл до клиента.

Тарифна логика: безплатна доставка над X € (конфигурируемо от админа), различна цена офис/адрес,
такса за наложен платеж, тегло по подразбиране на вариант (за да не се смята ръчно).

### 6.5. Плащания

| Метод | MVP | Коментар |
|---|---|---|
| Наложен платеж | ✅ задължително | 60–75% от BG fashion поръчките |
| Карта (Visa/Mastercard) | ✅ | **Stripe** за скорост на интеграция; **myPOS** или Borica през банката, ако таксите са решаващи. Решението е бизнес, не техническо — сравни такси още тази седмица, защото onboarding-ът е дълъг |
| Apple Pay / Google Pay | ✅ ако е Stripe (идва без допълнителна работа) | забележим лифт на мобилна конверсия |
| Банков превод | ➖ по избор | ниска употреба, но евтин |
| PayPal, BNPL | ❌ фаза 2 | слаб дял в BG |

Задължително: 3-D Secure 2, идемпотентност на плащането (двоен клик да не създава две поръчки),
webhook за потвърждение като единствен източник на истина (никога „redirect = платено“).

### 6.6. Връщания

По ЗЗП клиентът има **14 дни** за отказ. MVP: ясна страница + формуляр, който създава
`return_requested` в админа. Фаза 2: self-service портал с етикет за връщане.

## 7. Счетоводство / ERP / ОРАК

### 7.1. Оценка на четирите варианта

| | Какво е | Кога е правилно | Риск |
|---|---|---|---|
| **A. API към готов счетоводен софтуер** | Магазинът бута документи към Ажур L / Микроинвест / Бизнес Навигатор | Когато счетоводителят вече работи в този софтуер (най-често вярно) | Повечето български счетоводни продукти нямат модерен REST API — интеграцията реално е **файлов обмен** (CSV/XML/DBF) |
| **B. ERP / складова система** | ERP е истината за наличности, магазинът е канал | При 2+ склада, физически магазини, много доставчици | 3–6 месеца проект. За сегашния мащаб е трошене на срока |
| **C. Собствен счетоводен модул** | Пишеш си фактури, дневници, отчети | Почти никога в първа версия | ДДС, дневници покупки/продажби, VIES, ревизия — регулаторен риск, който не искаш да носиш |
| **D. Хибрид** | Магазинът е истината за поръчки и наличности; вътре има лек **документен модул** (фактури); счетоводството получава чист **експорт** | **Сега** | Нисък |

### 7.2. ПРЕПОРЪКА: **D (хибрид)** за MVP, с ясен път към A/B

**Във фаза 1 (до старта):**

1. **Вътрешен документен модул — минимален:**
   - проформа/фактура при плащане с карта; фактура при поискване за наложен платеж;
   - непрекъсната номерация по закон, отделни серии за фактура и кредитно известие;
   - задължителни реквизити по ЗДДС (ДДС номер, ЕИК, МОЛ, основание при 0%);
   - EUR като основна валута + BGN справочно, докато е задължително;
   - кредитно известие при връщане/сторно;
   - PDF генерация + автоматичен имейл + сваляне от админа.
2. **Финансов журнал (event log)** — всяко събитие с пари се записва неизменно:
   `order.paid`, `order.refunded`, `shipping.charged`, `cod.collected`, `discount.applied`.
   Това е слоят, който после храни *всяка* счетоводна система, каквато и да изберете.
3. **Експорт за счетоводителя** — един бутон „Период → експорт“, който дава:
   - `sales.csv` (документи), `items.csv` (редове), `payments.csv`, `returns.csv`;
   - формат, **съгласуван със счетоводителя преди да се пише** — това е задача за тази седмица;
   - автоматичен имейл на 1-во число за предходния месец.

**Фаза 2 (октомври–декември 2026):**
- Ако е Ажур L / ОРАК — правим директен конектор върху вече готовия финансов журнал. Първо трябва да
  се потвърди какъв обмен поддържа конкретната инсталация (файлов импорт, DB достъп, или API).
  **Действие сега:** поискай от счетоводителя точната версия и документация за импорт.
- Ако тръгнете към ERP (Микроинвест склад, Elit, или чужд) — Medusa става канал, ERP става истината за
  наличности; синхронизация през същия слой.

**Не пишете собствено счетоводство.** Пишете фактури и чист експорт. Разликата е между 2 седмици и 6 месеца.

### 7.3. Регулаторно — не пропускай (може да блокира старта повече от кода)

- **Наредба Н-18 / Приложение 33** — регистрация на електронния магазин в НАП **преди** започване на
  дейност; при промяна на софтуера се подава наново. Проверете задължението за подаване на стандартизиран
  одитен файл за електронния магазин.
- **Наложен платеж** — фискализацията е при куриера; уточнете писмено кой издава касовия бон.
- **ЗЗП** — 14-дневен отказ, стандартен формуляр за отказ, информация преди поръчката, бутон „Поръчка
  със задължение за плащане“.
- **GDPR** — Политика за поверителност, регистър на дейностите, договори с обработващи (куриер, платежен,
  имейл, аналитика), право на изтриване (бутон в админа).
- **Cookie consent + Google Consent Mode v2** — задължително за Google Ads/Analytics в ЕС. Без него
  ремаркетингът не работи законно.
- **Дигитални такси/ОРС** — линк към европейската платформа за онлайн решаване на спорове.
